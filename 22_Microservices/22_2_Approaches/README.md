## Задача 1: Обеспечить разработку

Предложите решение для обеспечения процесса разработки: хранение исходного кода, непрерывная интеграция и непрерывная поставка.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- облачная система;
- система контроля версий Git;
- репозиторий на каждый сервис;
- запуск сборки по событию из системы контроля версий;
- запуск сборки по кнопке с указанием параметров;
- возможность привязать настройки к каждой сборке;
- возможность создания шаблонов для различных конфигураций сборок;
- возможность безопасного хранения секретных данных (пароли, ключи доступа);
- несколько конфигураций для сборки из одного репозитория;
- кастомные шаги при сборке;
- собственные докер-образы для сборки проектов;
- возможность развернуть агентов сборки на собственных серверах;
- возможность параллельного запуска нескольких сборок;
- возможность параллельного запуска тестов.

Обоснуйте свой выбор.

### Ответ

Для обеспечения процесса разработки с хранением исходного кода, непрерывной интеграцией (CI) и непрерывной поставкой (CD), а также в соответствии с заданными требованиями, оптимальным решением будет использование комплексной облачной платформы DevOps, например, GitLab.

Обоснование выбора GitLab:
* Облачная система: GitLab предоставляет облачный сервис (GitLab.com) и возможность самостоятельно разворачивать сервер.
* Система контроля версий Git: GitLab построен на Git, с репозиторием под каждый сервис.
* Репозиторий на каждый сервис: легко создать отдельный репозиторий для каждого микросервиса.
* Запуск сборки по событию из Git: GitLab CI запускает пайплайны автоматически при push, merge и других событиях.
* Запуск сборки по кнопке с параметрами: можно запускать пайплайны вручную с вводом параметров (manual pipelines).
* Настройки на каждую сборку: расширенные возможности конфигурации с использованием переменных среды и параметров.
* Шаблоны для конфигураций сборок: поддержка шаблонов и переиспользуемых YAML-конфигураций.
* Безопасное хранение секретов: встроенное хранилище переменных с защищённым доступом.
* Несколько конфигураций сборки из одного репозитория: можно реализовать с помощью многоступенчатых пайплайнов и условий.
* Кастомные шаги сборки: полный контроль над скриптами и выполнением шагов.
* Собственные Docker-образы для сборок: поддержка Docker executor и возможность использования кастомных образов.
* Развёртывание агентов на своих серверах: GitLab Runner можно установить и управлять им на любом сервере.
* Параллельный запуск сборок и тестов: пайплайны и джобы могут выполняться параллельно для ускорения процесса.

### Взаимодействие компонентов
1) Хранение кода: каждый микросервис в своём Git репозитории на GitLab.
2) CI/CD пайплайны: на основании событий в репозитории (push, pull request) запускаются сборки и тесты в GitLab CI.
3) Параметризованные и ручные запуски: через интерфейс GitLab возможно запускать сборку вручную с доп. параметрами.
4) Секреты и настройки: код сборки использует переменные окружения для секретов и параметров.
5) Использование Docker образов: сборки выполняются в контейнерах, можно использовать свои образы для изоляции и воспроизводимости.
6) GitLab Runner: агенты сборки, расположенные как в облаке GitLab, так и на собственных серверах, обеспечивают масштабируемость и безопасность.


## Задача 2: Логи

Предложите решение для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор логов в центральное хранилище со всех хостов, обслуживающих систему;
- минимальные требования к приложениям, сбор логов из stdout;
- гарантированная доставка логов до центрального хранилища;
- обеспечение поиска и фильтрации по записям логов;
- обеспечение пользовательского интерфейса с возможностью предоставления доступа разработчикам для поиска по записям логов;
- возможность дать ссылку на сохранённый поиск по записям логов.

Обоснуйте свой выбор.

### Ответ

Для обеспечения сбора и анализа логов сервисов в микросервисной архитектуре оптимальным решением будет использование связки инструментов, основанной на стеке ELK (Elasticsearch, Logstash, Kibana) или EFK (Elasticsearch, Fluentd, Kibana), с учетом следующих принципов и компонентов:

### Компоненты решения и взаимодействие:
1) Сбор логов из stdout со всех хостов
* Для минимальных требований к приложениям логи собираются напрямую из stdout контейнеров или процессов.
* Агент сбора (Fluentd, Filebeat) устанавливается на каждом хосте/ноде, который агрегирует логи и отправляет их в централизованное хранилище.
2) Доставка логов в централизованное хранилище
* Через гарантированные протоколы передачи (например, TCP с повторной отправкой, Kafka или другие брокеры сообщений) обеспечивается надежная доставка логов.
* Elasticsearch используется как централизованное хранилище с возможностью горизонтального масштабирования.
3) Поиск, фильтрация и анализ логов
* Kibana предоставляет удобный веб-интерфейс для полнотекстового поиска, фильтрации и визуализации логов.
* Система позволяет создавать и сохранять пользовательские поисковые запросы и дашборды, которыми можно делиться через постоянные ссылки.
4) Доступ для разработчиков
* Через UI Kibana разработчики получают доступ к логам с разграничением прав по ролям.
* Можно настроить доступ по принципу "least privilege", предоставляя возможность только поиска и чтения.



## Задача 3: Мониторинг

Предложите решение для обеспечения сбора и анализа состояния хостов и сервисов в микросервисной архитектуре.
Решение может состоять из одного или нескольких программных продуктов и должно описывать способы и принципы их взаимодействия.

Решение должно соответствовать следующим требованиям:
- сбор метрик со всех хостов, обслуживающих систему;
- сбор метрик состояния ресурсов хостов: CPU, RAM, HDD, Network;
- сбор метрик потребляемых ресурсов для каждого сервиса: CPU, RAM, HDD, Network;
- сбор метрик, специфичных для каждого сервиса;
- пользовательский интерфейс с возможностью делать запросы и агрегировать информацию;
- пользовательский интерфейс с возможностью настраивать различные панели для отслеживания состояния системы.

Обоснуйте свой выбор.


### Ответ

Prometheus и Grafana — это ведущие open-source решения для мониторинга облачных и микросервисных инфраструктур. Prometheus предоставляет мощный движок сбора и хранения метрик с возможностью масштабирования и высокой отказоустойчивостью. Grafana обеспечивает удобный интерфейс для визуализации и анализа данных с поддержкой гибкой настройки панелей и прав доступа.

### Компоненты и принципы взаимодействия

Для мониторинга микросервисов и хостов оптимально использовать связку инструментов на базе Prometheus и Grafana:

- Prometheus — система сбора и хранения метрик с высокоэффективной временной базой данных.
- Сбор метрик состояния хостов (CPU, RAM, HDD, Network) с помощью экспортёров, например, node_exporter.
- Сбор метрик каждого сервиса через встроенные метрики, которые сервисы экспортируют в формате Prometheus.
- Поддержка сбора метрик, специфичных для сервисов, посредством кастомных экспортеров или библиотек для различных языков программирования.
- Гарантированная доставка метрик и масштабируемость благодаря pull-модели и возможности федерации данных.

- Grafana — платформа для визуализации и анализа данных.
- Предоставляет удобный пользовательский интерфейс для создания запросов к данным Prometheus.
- Позволяет создавать кастомные дашборды для мониторинга состояния всей системы.
- Обеспечивает разграничение доступа пользователей.
- Поддержка сохранения, экспорта и совместного использования ссылок на созданные дашборды и отдельные запросы.

## Взаимодействие компонентов:
1) На каждом хосте запускается node_exporter для сбора метрик состояния (CPU, RAM, HDD, Network).
2) Каждый микросервис экспортирует метрики в формате Prometheus.
3) Сервис Prometheus периодически опрашивает экспортеры на хостах и серверах, собирая метрики.
4) Данные сохраняются в базе Prometheus с временной меткой, обеспечивая агрегирование и хранение.
5) Операторы и разработчики используют Grafana для построения запросов, настройки дашбордов и визуализации состояния системы.
